## 脚本行为

程序通过 `subprocess.Popen` 启动，随后用 SDK `win32.get_list` 和 `window.get_detail()` 按该 PID 获取窗口。程序的工作目录设置为示例目录。不会因为同名窗口而采用别的进程。

第三步逐一校验“姓名”“城市（单选）”“城市（多选）”在新窗口中是否匹配。任意元素缺失时打印“元素没有找到”，退出码为 1，不进入第四步。全部存在时保留先前的范围检查和表单填写：姓名 `moby`、单选深圳、多选仅北京和广州，读回验证通过后退出码为 0。

关闭程序位于 `finally` 中，成功、元素缺失、库缺失和填写异常均执行。正常情况下使用 SDK `window.close()`，并通过 `Popen.wait` 确认进程退出；窗口尚未取得、SDK 关闭失败或关闭超时时，仅对本次创建的 `Popen` 进程执行 `terminate()` 并等待退出。最后释放 SDK 连接。

## 实测

| 场景 | 结果 | PID | 脚本退出码 |
| --- | --- | --- | --- |
| 真实用户库，新启动随机表单 | 三个元素均未找到，跳过填写，新进程已退出 | 117380 | 1 |
| 仅测试副本放宽随机 Pane 类名 | 正确填写和读回验证，新进程已退出 | 145820 | 0 |
| 元素库路径不存在 | 连接前报错，新进程已退出 | 156548 | 1 |

测试副本位于 `compatible-library`，仅将快照中随机的 `XPathWin32Panel_*` 类名条件从 required 移至 optional，保留窗口与控件名称等条件，作为成功分支的可匹配输入。未修改用户的 `element` 库。所有原库文件在本轮验证前后哈希一致。本轮开始时没有已运行的同类靶场进程，未据此声称额外覆盖同名旧进程的实测场景；脚本按 PID 选择和关闭的边界见实现。

进程退出由 Windows `OpenProcess` 和 `WaitForSingleObject` 独立检查，不仅依赖脚本的“已关闭”文字。语法检查通过，三分支验证程序退出码 0，详情见 `verification.json`。每个场景的命令、标准输出、标准错误均已保存。

当前真实库快照的两个 Pane 层将 `XPathWin32Panel_13637704116720261166` 列为 required；靶场每次启动都会随机改变 Pane 类名，因此本轮新进程没有匹配到三个保存元素。该结果符合用户要求的缺失分支，不能作为真实库重启后成功填写的证明。需要在 App 中调整这些随机类名的必选条件，才能跨启动稳定匹配；仅重新采集本次进程的随机类名仍会在下次启动时失效。

复测入口仍为示例目录中的 `uv run main.py`。没有修改产品源码或靶场源码，没有运行构建或依赖安装。
