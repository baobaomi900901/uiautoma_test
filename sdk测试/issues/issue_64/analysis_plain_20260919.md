# Issue #64：为什么 find / find_all 找不到——通俗版

## 问题出在“从哪里开始找”

网页上确实有这些控件。你的页面级定位、DOM 检查，以及四个 CSS/XPath 查找测试都已经证明了这一点。

把网页想成一栋楼：

- 整个页面是楼的大门。
- iframe 是楼里的一间办公室。
- Shadow DOM 是办公室内的一块独立区域。
- 文本框、密码框等控件就在这个区域里。

元素库保存的是一份完整路线：“从大门进去 → 找到办公室 → 进入独立区域 → 找到输入框”。

当你调用 `page.find(元素名)` 时，程序从大门出发，路线对得上，所以能找到。

当你调用 `root.find(元素名)` 或 `root.find_all(元素名)` 时，程序已经来到办公室里面，却仍然照着“从大门出发”的完整路线，再找一次外面那间办公室的入口。程序换了出发地点，但没有相应调整路线。

这就是本次源码分析定位到的问题。

## 为什么 CSS 和 XPath 能成功

这些调用给的是当前位置附近的查找条件，例如：

```python
root.find_by_css("input#form-controls-ant-text")
root.find_by_xpath(".//input[@id='form-controls-ant-text']")
```

它们相当于：“已经在这里了，就找这里面的那个输入框。”不需要重新走元素库保存的外层路线，因此本轮能够成功。

把名称换成 Selector 对象没有改变路线。两种写法最终取的仍是同一份保存记录。

## 为什么一个报错，另一个返回空列表

- `find()` 约定必须找到一个元素，找不到就抛 ElementNotFoundError。
- `find_all()` 约定返回列表，找不到就返回 []。

两种表现来自同一次“走错起点后的未命中”，不是两个不同的问题。

你的 `find_all` 结果为 25/32：四种输入框、Selector、零超时和多项查找这七个正向用例都失败。其它准备、错误参数和清理用例通过，并不能抵消这些核心功能失败。

## 现在该如何理解这个结果

继续增加等待时间解决不了路线起点的问题。本轮已经有六项等满约 5 秒仍然返回空列表。

需要开发侧处理 [Issue #64](https://github.com/uiautoma/desktop/issues/64)：让保存的定位路线与当前查询位置正确配合，并且查到的元素仍必须属于指定 root。

本轮不应把“应该找到但返回空”的结果改成通过，也不能说整个 SDK 都不会查 iframe／Shadow DOM——你刚刚通过的 CSS／相对 XPath 测试已经说明这类节点是可以操作的。

还要分开看一处测试脚本问题：旧 `find_form.py` 把运行时显示名称与元素库名称作相等比较，这个要求不可靠。但日志里的 Selector 调用是在名称比较之前就报“未找到”，所以它仍能证明查找本身有问题。
