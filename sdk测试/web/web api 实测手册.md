# Web API 实测手册

本文件是 [`../AGENTS.md`](../AGENTS.md) 「TEST WORKFLOW」的细则与模板，按需查阅；
步骤本身在 `AGENTS.md` 里，本文件只放「怎么做才对」的判据、手法与骨架。

---

## 1. 结论口径：状态模型与生命周期

脚本内每个用例只允许四种状态，最后汇总成退出码：

| 状态 | 含义 | 计入退出码 |
|---|---|---|
| `PASS` | 实测结果与判据一致 | 是（通过） |
| `FAIL` | 与判据不一致，且已排除判据错与环境抖动 | 是（失败） |
| `BLOCKED` | 环境不具备（外网不可达、靶场页缺失、元素库缺条目），**不是产品结论** | 是（阻塞） |
| `KNOWN` | 已如实刻画的边界或他人缺陷（例如底层平台能力边界、其他 API 的已知问题） | 否 |

退出码：`0` = 全部 PASS（允许 KNOWN）；`1` = 存在 FAIL；`2` = 无非 FAIL 但存在 BLOCKED。

API 生命周期（与 `AGENTS.md`「PUBLIC DOCUMENTATION GATE」一致）：
`DRAFT` → `READY_FOR_LIVE` → `VERIFIED`。只有**真实场景**与**资源清理**都 `PASS` 才写 `VERIFIED`；
存在未解决缺陷时写 `READY_FOR_LIVE` 并把缺陷如实写进证据文档。

## 2. 期望值从哪来（决定验收可信度）

只允许三类来源，**禁止**把「产品自己的返回」当期望值：

1. **活推导**：从页面/DOM/文件系统现场读出应有的值。例：先用 `execute_javascript` 读
   `scrollWidth/scrollHeight`，再断言截图尺寸等于它；先用 `find_all` 数出匹配数量，再断言后续行为。
2. **独立推导**：手写期望值，依据是**公开规范**而不是实现。例：注入受控 HTML 后按 `innerText`
   语义手推换行/折叠/隐藏，直接写死期望字符串；HTTP 响应字节按 HTTP 语义手推。
3. **独立确证**：用**与产品无关的通道**核对结果。例：`ctypes` 直读剪贴板、`urllib` 独立下载后逐字节比对、
   第三方回显服务读回服务端实收内容、解析 PNG/JPEG/DIB 字节、`web.get_all()` 复核标签、
   `performance.timeOrigin` 判断是否真的重新加载。

一句话判据：**如果被测产品返回了错误结果，我的断言会不会跟着一起错？** 会 → 换来源。

## 3. 独立确证手法速查

| 被测对象 | 独立通道 |
|---|---|
| 截图/剪贴板图片 | 解析文件字节（PNG IHDR / JPEG SOF）；`ctypes` 读 `CF_DIB` 头与像素；与同参文件截图做三角像素比对 |
| 文本/HTML/属性 | 与页面内 `innerText`/`textContent`/`getAttribute` 对照（真实元素）；受控 fixture 用手推期望值 |
| 导航/加载状态 | `web.get_all()` 列表、`document.readyState`、`performance.getEntriesByType('navigation')`、耗时区间 |
| 网络请求 | 第三方回显服务读回 `data`/`headers`/`url`；非 2xx 用同源静态文件构造；大文件用 `bytes/N` |
| 剪贴板 | `ctypes` 直读/直写，并与进入时快照比对（收尾还原） |
| 元素存在性/可见性 | DOM 查询与 `getClientRects()`/`computedStyle` 对照；显式区分「存在」与「可见」 |
| 时间类语义（超时/等待） | 断言**耗时区间**而不只看返回值；同时记录失败形态 |

## 4. 抖动治理（不要让偶发假失败污染结论）

先判断抖动的**来源层级**，再选手段；一律把实测值写进报告：

| 现象 | 手段 |
|---|---|
| 读取器被环境占用（剪贴板/进程） | 读取器内部重试（如 20×0.25s），仍失败记 `BLOCKED` |
| 页面渲染单像素级抖动 | 三角比对：同参数连取两份参考，许可差异 = 实测抖动 + 小预算；三组数值全进报告 |
| 瞬时引擎错误（如 `page_runtime_probe_timeout`、`frame_not_found`） | 先做**上下文预热**（导航后先做一次 DOM 查询），再对该用例重试；真用到重试时输出 `KNOWN` 并记录 trace |
| 目标本身按周期变化（自计时页） | 用「确认状态 → 立即开始等待」的时序，超时取小于周期的值留余量 |
| 判断「加载完成」类布尔值有多种成因 | 用**组合判据**区分（如 `is_load_completed()` 为 False 时再看 `execute_javascript` 是否可用），不用单一布尔值 |

反模式：把偶发当缺陷提单；或为了让脚本变绿而放宽到掩盖真实偏差（预算必须小到不足以掩盖系统性错误）。

## 5. FAIL 三分法

出现 FAIL 先按这三类定性，并在报告里给出依据：

1. **产品缺陷**：可用最小复现稳定复现，且判据来自公开语义。→ 按第 6 节走 Issue 交接，脚本里该项如实记 `FAIL`，
   证据文档写「已知缺陷 + 复现步骤 + 原始 trace」。
2. **我的判据错**：期望值来源不当、时序假设错、把实现细节当规范。→ 修脚本与证据文档，
   并在证据文档里保留「修正记录」（原先期望什么、为什么错、改成什么）。
3. **环境抖动**：见第 4 节。→ 加固判据并记录，不写成缺陷。

**禁止**为了让结果好看而：删掉失败用例、把 FAIL 改成 PASS、把未测项说成通过。

## 6. 靶场与元素库规则

- **测试侧不自建靶场**。需要页面/元素时，向用户提出**可直接使用**的需求：页面用途、建议文件名、
  可复制的完整 HTML、需要暴露的自证信息（如状态元素、计数属性）。
- 靶场源码仓库（`baobaomi900901/xpath`）默认**只读**；仅在用户明确授权时才写入，
  且要登记到靶场目录页（`WEB/src/pages/HomePage.tsx` 的 `menuItems`），提交信息写明用途。
- 靶场是 GitHub Pages 静态托管：**做不了服务端回显/延迟**，需要回显就改用外部回显服务，
  或请用户加前端页面。
- 元素库（`260902_web元素`）由用户在桌面应用中采集；SDK **没有**公开的「新增元素」接口
  （`capture`/`validate` 为暂缓模块），需要新元素时按上一条提出需求。
- 优先使用用户为某 API 专门准备的库元素：脚本先 `find(名称)`，再用 `get_attribute("id")`
  核对它指向的 DOM 节点，把映射写进报告。

## 7. 副作用与清理（每次必须自证）

| 资源 | 要求 |
|---|---|
| 浏览器标签 | 关闭本次页面后用 `web.get_all()` 复核无残留；对「不可关闭」的场景（无响应页面）记 `KNOWN` 并说明 |
| 剪贴板 | 进入时快照文本/图像，收尾还原；进入时为空则保留最后一次验收产物并写明 |
| 临时目录 | 库副本、截图、落盘文件都写在 `.pytest_tmp/<run_id>/`，收尾整目录删除 |
| 注入的 DOM 探针 | 收尾用 JS 移除（`#uiautoma-*` 前缀统一命名），不留痕 |
| 元素库 | 只操作本工作区的**副本**，绝不改用户原件 |
| 被测源码 | 只读；需要给出源码线索时标注 worktree 路径与 commit |

收尾还要有一次「环境状态」自检：标签数与进入时一致、`.pytest_tmp` 为空、仓库干净。

## 8. 脚本骨架

命名：`web/test_web_<browser|element>_<api>.py`（下划线小写；同族 API 用同前缀）。
结构固定为：

```python
def check_contract(): ...        # inspect 签名/默认值/返回注解，与源码合同逐项比对
def run(args):
    results = [check_contract()]
    # 1 环境基线（标签数、进入时快照）
    # 2 准备（元素库副本 / 页面打开 / 目标元素绑定与指向核对）
    # 3 正向路径（能覆盖「等待/转变」的要给出 canonical 场景）
    # 4 语义矩阵（活推导 / 独立推导 fixture；同时记录对照值）
    # 5 参数校验（非法类型、越界、多余/缺失参数；断言类型 + 消息片段 + 立即返回）
    # 6 生命周期（关闭后调用、无 Package、失效引用）
    # 7 收尾（清理 + get_all 复核 + 临时目录删除），单独一条 cleanup 用例
    return results, code             # 0/1/2
```

约定：
- CLI 至少有 `--contract-only`、`--json`，以及可复测的 URL/库路径参数。
- `--json` 输出归档到 `web/evidence/artifacts/<api>_<yyyymmdd>.txt`（UTF-8）。
- 每条用例的 `detail` 要能单独读懂：**测什么、期望什么、实测什么、耗时多少**。
- 断言消息里放实测值，不放「失败」两个字。
- 脚本顶部 docstring 写：靶场/页面/元素库、期望值来源、源码要点、退出码约定。

## 9. 证据文档骨架

路径：`web/evidence/<api>.md`。五要素必备：

1. **用途与合同**：签名表（含默认值与返回类型）。
2. **真实验收结果**：`N/N 通过 + 边界项，退出码 0`，是否连续多次全绿，靶场、被测 worktree + commit。
3. **期望值来源与独立确证**：本文第 2、3 节用的哪几种，具体怎么做的。
4. **实测行为记录 / 已知边界**：值得复测者知道的语义、注意事项、他人缺陷（附 Issue 链接）。
5. **复测**：脚本路径、产物路径、可直接粘贴的命令、退出码约定。

补充规则：
- 与既有结论冲突时**按修订记录写**：保留原结论、写明「原排除项已撤销/原计数已订正」及原因，不要悄悄改。
- 边界与缺陷要写清「谁负责」：属本 API 的写进本文件，属其他 API/平台的记 `KNOWN` 并交叉链接。
- 「明确排除」一节要诚实列全未覆盖场景（模式、DPI、超大输入、异常路径）。

## 10. Git 与汇报

- 一次提交**只含一个 API** 的东西：脚本 + 证据 + 产物 + 两处索引。
- `git add` **逐条写显式路径**。写错路径会让整批 `add` 中止，导致只提交部分文件
  （实测踩过：一次只进去了 1 个文件），所以提交前用 `git diff --cached --name-only` 复核。
- 提交信息用中文，含**结果数字**（如 `42/42`）与关键覆盖点；推送后确认 `git status` 干净。
- 汇报固定结构：结果数字 → 独立确证方式 → 发现与边界（含是否提单）→ 交付物与提交号 → 收尾状态 → 下一个候选。

## 11. 判据反模式清单

- 只看返回值不看**副作用**（返回 `None` 的 API 必须另找可观测状态）。
- 把「我的实现细节」当期望值（例如照抄源码里的常量、阈值、错误文案顺序）。
- 硬性 0 容忍（字节/像素完全相等）而不看抖动实测值。
- 用单一布尔值判断有多种成因的状态（加载中 vs 错误页）。
- 清理只「调用」不「复核」（调了 `close()` 就记 PASS，不查标签，也不查临时目录）。
- 把环境阻塞写成缺陷，或把缺陷写成环境问题。
- 未测却说已测；覆盖不到的就说清楚「明确排除」。
