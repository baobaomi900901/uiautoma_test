# Web API 测试清单与复测计划

## 统一输出约定

Web API 脚本沿用 Win32 验收输出：终端显示 API、页面、元素库、进度表、逐项状态、耗时、失败原因、资源清理和最终退出码；双侧表单 API（Ant/原生）由总入口分别汇总。子脚本的完整 JSON stdout/stderr 仅保存到 `web/.logs/`，避免终端刷屏。

日期：2026-09-11。目标：使用当前选定 Desktop worktree 的 SDK、当前 UIAutoma
dev Web Stack 和可复现测试页面，逐项重新完成 Web API 真实验收。每项单独准备脚本、
执行日志和证据；通过后由测试者确认，再更新 `web/evidence/<api>.md` 与索引。

## 当前规模

- 索引中已有 Web API：39 个。
- 已有 VERIFIED：21 个，建议在当前基线重新复验。
- READY_FOR_LIVE：18 个，优先处理。
- 源码中尚未进入当前索引的顶层 Web API：13 个，需先完成合同和场景设计。
- 当前 Web 证据不能自动视为当前基线结果；每项都以本次真实日志为准。

## 执行规则

每项按以下顺序执行：读取当前源码签名 → 确认测试页面/元素 → 编写或调整测试脚本 →
静态语法检查 → 真实运行 → 检查资源清理 → 测试者确认 → 更新证据和索引。

每个脚本顶部记录 API 参数（区别于脚本参数），命令统一支持 `--non-interactive`；
需要浏览器人工操作时明确写出。失败分为产品缺陷、测试脚本错误和环境阻塞，不把失败
改写为通过。每次测试记录浏览器、页面、元素选择器、浏览器扩展/Native Host状态、
超时、异常类型、截图/下载临时目录和清理结果。

## 每项验收模板

1. API 合同：签名、默认值、位置/关键字规则、返回类型。
2. 环境准备：浏览器/页面/元素可用，扩展和桥接状态明确。
3. 正常路径：默认、关键字、边界和代表性数据。
4. 参数边界：空值、非法值、超时、重复调用和未找到。
5. 独立交叉校验：DOM/原生浏览器状态、文件系统或剪贴板；避免只验证 SDK 自己的回读。
6. 副作用与清理：页面、Cookie、下载、上传、弹窗、浏览器进程和临时资源恢复。
7. 结果：输出通过数/总数、耗时、退出码、失败分类和未覆盖范围。

## 建议推进方式

下一项从 `WebElement.check()` 开始。每完成一项，只推进该项的脚本、真实运行和证据；
遇到失败先诊断，不同时修改多个 API。对于需要真实浏览器扩展的项目，先确认当前
Web Stack 能连接，再进入 API 调用。发现产品缺陷时提交 issue，并把复现与证据链接
写回对应证据文档。

## 当前已知风险

- Web 证据中部分条目来自历史基线，不能直接替代当前版本复测。
- `handle_save_dialog()` 历史上存在 `wait_complete=True` 超时记录，必须保留失败分支。
- 多选、下载、上传和Cookie测试都可能修改外部状态，必须先保存并在finally恢复。
- 浏览器页面关闭、扩展重载和焦点恢复属于环境状态；不能与 API 业务结果混为一项。
